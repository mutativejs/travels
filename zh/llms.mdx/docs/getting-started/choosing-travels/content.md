# 选择合适的方案 (/zh/docs/getting-started/choosing-travels)

Travels 围绕一个明确的取舍而设计：把一部分计算花在生成与应用补丁上，以缩小保留历史、让完整时间线的持久化变得可行。它并不打算在每一项更新延迟基准上都胜出。

## 按工作负载选择 [#按工作负载选择]

| 场景 | 推荐方案 |
| --- | --- |
| 状态很大，编辑只涉及局部 | Travels：保留补丁通常可以避免反复复制完整状态 |
| 历史很长，并且必须在刷新后依然存在 | Travels：一个带版本的快照同时包含状态与历史 |
| 需要可重放的操作日志或撤销元数据 | Travels：条目包含正向/反向补丁与元数据 |
| 状态很小，只需几条本地历史 | 快照栈、Redux-undo 或 Zundo 可能更简单也更快 |
| 每次编辑都会替换大部分或全部状态 | 两种方案都测一测；补丁成本可能接近快照 |
| 需要多人协作合并与并发冲突消解 | 使用 CRDT/OT 系统；Travels 本身不负责消解冲突 |

## 比较成本 [#比较成本]

快照历史会为每个条目支付一次状态复制成本，导航通常很便宜。补丁历史需要支付生成与应用补丁的成本，但对于局部更新，它只保留发生变化的操作。

在 Travels 中，不可变更新还会借助 Mutative 的结构共享。“基于补丁”并不意味着每个保留状态都被深拷贝，“更小的历史”也不代表 `setState()` 的延迟一定最低。

请围绕四个维度测量你的真实工作负载：

1. 更新延迟与吞吐量。
2. 撤销/重做与事务的延迟。
3. 保留及序列化后的历史体积。
4. 保存、恢复与语义校验的成本。

仓库中的[基准测试套件](https://github.com/mutativejs/travels/tree/main/benchmarks)把这些关注点分开测量，而不是给出一个放之四海皆准的赢家。

## 选择所有权模型 [#选择所有权模型]

### `createTravels()` [#createtravels]

当 Travels 应当接收并提交更新时使用它。这是原生状态、reducer 风格状态以及大多数新集成的默认选择。

- 不可变模式返回新的状态引用。
- 可变模式直接更新活动对象，适用于 MobX、Vue、Pinia 等响应式所有者。
- 可以使用 `setState()`、事务、跟踪控制与 `getControls()`。

### `createTravelJournal()` [#createtraveljournal]

当另一个运行时已经能生成 `nextState`、`patches` 与 `inversePatches` 时使用它。外部所有者仍然是权威来源。

- 用 `recordPatches()` 记录一次已有的提交。
- 通过必需的同步 `apply` 回调执行撤销/重做。
- 避免重复生成同一组补丁。
- 不要把委托的导航结果再次传回 `recordPatches()`。

提交与失败边界见[Journal 指南](/zh/docs/guides/controlled-journal)。

## 选择归档模式 [#选择归档模式]

- **自动（`autoArchive: true`）**：每次有效的 `setState()` 调用都是一个撤销步骤。这是默认值，也是大多数应用的合适起点。
- **手动（`autoArchive: false`）**：更新会立即影响当前状态，而 `archive()` 把待处理的工作合并为一个条目。适用于输入框失焦提交、拖拽手势或应用自定义的事务边界。

如果一次原子操作只需要向观察者发布一个最终事件，优先使用 `transaction()`，而不是手动协调归档。

## 实用决策清单 [#实用决策清单]

如果以下大多数问题的答案都是“是”，Travels 很可能适合你：

- 撤销/重做是产品功能，而不只是调试便利？
- 更新通常小于完整状态？
- 历史需要元数据、持久化或重放？
- 带版本的快照能简化本地优先存储？
- 你同时需要不可变集成与引用稳定的响应式集成？

如果你的唯一需求只是在一个组件里保留五步计数器历史，那么一个小的本地栈大概就够了。
